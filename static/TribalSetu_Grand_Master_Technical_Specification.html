## 1. EXECUTIVE SUMMARY & PROBLEM STATEMENT ANALYSIS

### 1.1 Official Problem Statement (PS ID: 26239)
> *"The implementation of these schemes involves multiple stages, including applicant registration, online application, document submission, eligibility verification, scrutiny, screening, selection, communication, and post-selection/fellowship management. At present, several stages involve manual scrutiny, repeated correspondence and multiple levels of verification, resulting in processing delays, repetitive administrative effort, limited real-time visibility and scope for errors in verification and workflow management."*

### 1.2 Target Schemes & Annual Impact Metrics
1. **PMS-ST (Post-Matric Scholarship for ST Students):**  
   - Beneficiaries: ~90 Lakh tribal students across 36 States/UTs.  
   - Pain Point: Heavy delays (3 to 8 months), bogus certificates, manual revenue-stamp inspection.
2. **NFST (National Fellowship for Higher Education of ST Students):**  
   - Beneficiaries: 750 fresh M.Phil/Ph.D. research fellowships annually.  
   - Pain Point: Post-selection monthly stipend release requires physical supervisor signatures, leading to scholarship disbursement delays of up to 6 months.
3. **NOS (National Overseas Scholarship for ST Students):**  
   - Beneficiaries: 20 international study slots annually.  
   - Pain Point: Complex manual slot allocation, visa/offer-letter authentication, and strict merit-cum-means compliance.
4. **NESTS (National Education Society for Tribal Students - EMRSs):**  
   - Beneficiaries: Eklavya Model Residential School students transitioning to higher secondary education.

### 1.3 Core Failure Modes of Existing Systems (NSP & State Portals)
- **Zero Pixel-Level Tampering Detection:** Scanned fake certificates with edited marks, spliced incomes, and Photoshop-modified names pass through traditional OCR systems because OCR only parses visible text, completely ignoring JPEG compression anomalies.
- **Synchronous Server Bottlenecks:** When 15 Lakh students log in 48 hours before the application deadline, synchronous PHP/.NET application servers crash due to thread exhaustion, database connection pool starvation, and file I/O locks.
- **Fragmented Identity Verification:** Applicant names differ slightly across documents (`Rahul Kumar Munda` on Aadhaar vs. `Rahul Munda` on 10th Marksheet vs. `R. K. Munda` on Caste Certificate), triggering manual rejection or endless re-scrutiny cycles.
- **DBT Transaction Failures:** Scholarships are sanctioned on paper, but bank payouts bounce at the Public Financial Management System (PFMS) stage because the student's bank account is not mapped to the NPCI Aadhaar Payment Bridge (APB).

       │
       ▼
[Stage 3: Dual-Engine QR Scan] ────────► zxing-cpp industrial decode (RSA-2048 Gov Cryptographic Token)
       │
       ▼
[Stage 4: OCR Entity Extractor] ───────► Tesseract + Regex entity parsing (Hindi/English certificate keys)
       │
       ▼
[Stage 5: Article 342 Validator] ──────► In-memory state-wise ST gazette hash verification (O(1) lookup)
       │
       ▼
[Stage 6: Identity Matcher] ───────────► Cross-document fuzzy matching (Levenshtein Token Sort Ratio)
       │
       ▼
[Stage 7: NPCI DBT Verifier] ──────────► Aadhaar-bank account seeding status validation
       │
       ▼

## 4. MATHEMATICAL & ALGORITHMIC FOUNDATIONS

### 4.1 Error Level Analysis (ELA) Forensic Formulation
When a JPEG image is saved, its discrete cosine transform (DCT) coefficients are quantized according to an 8×8 block frequency matrix. If an attacker opens a genuine certificate in Photoshop, alters the income figure from `₹1,80,000` to `₹45,000`, and re-saves the file, the newly modified pixels undergo their first generation of compression, while the unmodified surrounding pixels undergo their second generation of compression.

1. **Compression Error Grid:**  
   Given original image $I_{\text{orig}}$ and standard recompressed baseline image $I_{\text{baseline}} = \mathcal{Q}_{90}(I_{\text{orig}})$:
   $$\Delta(x, y) = |I_{\text{orig}}(x, y) - I_{\text{baseline}}(x, y)|$$
2. **Local Patch Variance:**  
   Divide the grayscale difference map $\Delta_{\text{gray}}$ into an $N \times M$ grid of patches $P_{i,j}$ of dimensions $w_p \times h_p$:
   $$\sigma_{i,j} = \sqrt{\frac{1}{w_p h_p} \sum_{x \in P_{i,j}} \sum_{y \in P_{i,j}} (\Delta_{\text{gray}}(x, y) - \mu_{i,j})^2}$$
3. **Anomaly Ratio ($R_{\text{tamper}}$):**
   $$R_{\text{tamper}} = \frac{\max_{i,j}(\sigma_{i,j})}{\frac{1}{N M} \sum_{i,j} \sigma_{i,j} + \epsilon}$$
   - **Decision Rule:** If $R_{\text{tamper}} > 2.8$ and $\max(\Delta) > 35$, the document is mathematically classified as **Digitally Tampered** ($\text{TamperScore} = \min(R_{\text{tamper}} \times 25.0, 96.0)$).

### 4.2 Composite Trust Score Algorithm
The comprehensive multi-criteria trust engine uses a weighted sum model:

$$\text{TrustScore} = w_{\text{QR}} S_{\text{QR}} + w_{\text{ELA}} S_{\text{ELA}} + w_{\text{ID}} S_{\text{ID}} + w_{\text{Gazette}} S_{\text{Gazette}} + w_{\text{DBT}} S_{\text{DBT}}$$

#### Rigorous Weight Distribution:
$$\begin{aligned}
w_{\text{QR}} &= 0.30 \quad (\text{Cryptographic digital signature verification}) \\
w_{\text{ELA}} &= 0.25 \quad (\text{Pixel-level compression forensics, } S_{\text{ELA}} = 100 - \text{TamperScore}) \\
w_{\text{ID}} &= 0.20 \quad (\text{Cross-document fuzzy token identity similarity}) \\
w_{\text{Gazette}} &= 0.15 \quad (\text{Constitution Article 342 statutory Scheduled Tribe verification}) \\
w_{\text{DBT}} &= 0.10 \quad (\text{NPCI Aadhaar Payment Bridge bank seeding status})
\end{aligned}$$

$$\sum_{i} w_i = 0.30 + 0.25 + 0.20 + 0.15 + 0.10 = 1.00$$

#### Triage Classification Boundaries:
$$\text{TriageDecision} = \begin{cases} 
\mathbf{GREEN} \text{ (Auto-Approve / Instant PFMS Batch)}, & \text{if } \text{TrustScore} \ge 85.0 \land S_{\text{ELA}} \ge 75.0 \land S_{\text{Gazette}} = 100 \\
\mathbf{YELLOW} \text{ (Officer Manual Review / 10s Queue)}, & \text{if } 60.0 \le \text{TrustScore} < 85.0 \lor \text{Doc} = \text{Handwritten} \\
\mathbf{RED} \text{ (Fraud Flagged / Rejection Audit)}, & \text{if } \text{TrustScore} < 60.0 \lor S_{\text{Gazette}} = 0 \lor S_{\text{ELA}} < 50.0
\end{cases}$$

### 4.3 Fuzzy Identity Matching Formulation (Token Sort Levenshtein)
Given strings $S_1$ (e.g. Aadhaar name) and $S_2$ (e.g. Caste Certificate name):
1. Preprocess: Lowercase, remove special characters, tokenize into word sets $T_1$ and $T_2$.
2. Sort tokens lexicographically: $T_1^* = \text{sort}(T_1)$, $T_2^* = \text{sort}(T_2)$.
3. Re-join into strings: $S_1^* = \text{join}(T_1^*)$, $S_2^* = \text{join}(T_2^*)$.
4. Compute normalized Levenshtein ratio:
   $$\text{Ratio}(S_1^*, S_2^*) = \left( 1 - \frac{\text{LevenshteinDistance}(S_1^*, S_2^*)}{\max(|S_1^*|, |S_2^*|)} \right) \times 100$$
   - A threshold of $\ge 75\%$ accounts for legitimate Indian naming variations (e.g. `Munda Birsa` vs `Birsa Munda`).

## 5. SECURITY, CRYPTOGRAPHY & DPDP ACT 2023 COMPLIANCE

```
┌────────────────────────────────────────────────────────────────────────┐
│               DPDP ACT 2023 ZERO-KNOWLEDGE AADHAAR VAULT                │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│  [Uploaded Aadhaar Card / Camera Capture]                              │
│                      │                                                 │
│                      ▼                                                 │
│  [Client-Side / In-Memory Ingestion Worker]                            │
│  - Regex / Spatial OCR identifies: 12-Digit Pattern (\d{4} \d{4} \d{4})│
│                      │                                                 │
│                      ├──► [Masking Engine]                             │
│                      │    - Replaces first 8 digits with 'X'           │
│                      │    - Output: "XXXX-XXXX-9012"                   │
│                      │    - Stored in Relational DB                    │
│                      │                                                 │
│                      └──► [Salted Cryptographic Hash]                  │
│                           - SHA-256 (AadhaarNumber + MinistrySalt)     │
│                           - Irreversible 64-char Hex String            │
│                           - Used exclusively for deduplication checks  │
│                                                                        │
│  * RAW 12-DIGIT AADHAAR NUMBER NEVER COMMITTED TO DISK STORAGE *       │
└────────────────────────────────────────────────────────────────────────┘
```

1. **Digital Personal Data Protection (DPDP) Act 2023 Conformance:**  
   - Strict purpose limitation: No raw 12-digit Aadhaar number is stored in plaintext on disk, databases, or logs.
   - Irreversible SHA-256 salted hashes allow exact 1:1 duplicate detection without exposing the underlying identity.
2. **Data-at-Rest Encryption (DAR):**  
   - Uploaded binary documents stored in S3/MinIO are encrypted using **AES-256-GCM** with per-file envelope encryption. Master keys are managed via hardware security modules (HSM) or cloud KMS.
3. **Data-in-Transit Encryption (DIT):**  
   - All network calls enforce **TLS 1.3** cipher suites (`TLS_AES_256_GCM_SHA384`).
   - Administrative communication between State Nodal Officers and Ministry endpoints enforces mutual TLS (mTLS).
4. **Tamper-Proof Audit Trail (Append-Only Ledger):**  
   - Every officer decision, manual review, and AI verification output creates an immutable cryptographic log entry:
   $$\text{Hash}_n = \text{SHA256}(\text{Hash}_{n-1} + \text{Timestamp} + \text{OfficerID} + \text{Action} + \text{TrustScore})$$
   - Prevents retroactive tampering with application approvals or fraud dismissals.

## 6. HIGH-CONCURRENCY SCALABILITY ARCHITECTURE (20+ LAKH PEAK LOAD)

### 6.1 The Deadline Day Challenge
In national scholarship portals (NSP/PMS), 70% of total submissions arrive within the final 72 hours before the deadline. A volume of 20,00,000 applications over 72 hours yields an average of **27.7 submissions per second**, with peak burst traffic reaching **250 to 500 requests per second (RPS)**.

### 6.2 Asynchronous De-Coupling via Task Queuing
Traditional systems fail because they execute image pre-processing, OCR, and database updates synchronously within the HTTP request thread. TribalSetu implements strict decoupling:

```
[Student Browser]
       │  POST /api/verify-and-apply (Multipar/form-data)
       ▼
[NGINX Load Balancer] (SSL Termination, Rate Limit, Fast GZIP)
       │
       ▼
[FastAPI Gateway Instances] (4 Worker Processes per CPU Core)
       │
       ├──► 1. Save uploaded file buffer to S3 / Object Store (50ms)
       ├──► 2. Generate UUIDv4 Task ID (1ms)
       ├──► 3. Push Job Payload {task_id, file_uri, applicant_meta} to REDIS (2ms)
       │
       ▼
[HTTP 202 Accepted Response] (Returned to student in < 80 milliseconds)
       │
       ▼
[Client Polls / WebSocket] ──► Listens to /api/tasks/{task_id}/status every 2 seconds
```

### 6.3 Worker Pool Auto-Scaling Calculations
- Execution time of 8-stage AI Pipeline per document: $\approx 2.5 \text{ seconds}$ on 1 CPU Core.
- Single 8-Core Worker Node capacity: $8 \text{ cores} / 2.5 \text{s} = 3.2 \text{ verifications/second} \approx 11,520 \text{ docs/hour}$.
- To process peak burst of 300 RPS:
  $$\text{Required Worker Cores} = 300 \text{ RPS} \times 2.5 \text{s} = 750 \text{ Cores}$$
  - Distributed across **46 Kubernetes Pods** (each allocated 16 vCPUs, 32GB RAM).
  - Kubernetes Horizontal Pod Autoscaler (HPA) triggers scaling based on the **Redis Queue Length metric** (`redis_queue_unprocessed_jobs > 500`).
  - Total processing time for 20 Lakh applications across 750 worker cores: $\approx 4.6 \text{ hours}$.

### 7.2 The Cascading Early-Exit Optimization
To ensure maximum resource conservation, the pipeline does not execute all 8 stages if a fatal fraud indicator is discovered early:
1. **Early Exit 1 (Non-ST Claim):** If OCR extracts a caste explicitly non-ST (e.g. `Brahmin`, `Rajput`), Stage 5 triggers immediate failure. Stages 6, 7, and 8 are bypassed, saving 70% compute.
2. **Early Exit 2 (Photoshop Splicing):** If ELA tamper score exceeds 90%, the document is routed directly to the Red Fraud Queue without wasting cycles on fuzzy matching or bank validation.

## 10. RELATIONAL DATABASE SCHEMA (POSTGRESQL DDL & ERD)

```sql
-- ====================================================================
-- TRIBALSETU ENTERPRISE RELATIONAL SCHEMA (POSTGRESQL 16)
-- ====================================================================

CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

-- 1. USERS & ROLES TABLE
CREATE TYPE user_role AS ENUM ('STUDENT', 'INO', 'DWO', 'SNO', 'MOTA_ADMIN', 'SUPERVISOR');

CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    email VARCHAR(255) UNIQUE NOT NULL,
    phone VARCHAR(15) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    role user_role NOT NULL,
    aadhaar_hash CHAR(64) UNIQUE NOT NULL, -- SHA-256 Salted Hash (Zero Knowledge)
    full_name VARCHAR(255) NOT NULL,
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 2. SCHEMES MASTER TABLE
CREATE TABLE schemes (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    scheme_code VARCHAR(50) UNIQUE NOT NULL, -- 'PMS-ST', 'NFST', 'NOS'
    name VARCHAR(255) NOT NULL,
    ministry VARCHAR(255) DEFAULT 'Ministry of Tribal Affairs',
    academic_year VARCHAR(20) NOT NULL,
    max_annual_income NUMERIC(12, 2) NOT NULL, -- e.g. 250000.00 for PMS-ST
    st_category_mandatory BOOLEAN DEFAULT TRUE,
    total_slots INT, -- NULL for entitlement schemes (PMS), 750 for NFST, 20 for NOS
    is_active BOOLEAN DEFAULT TRUE
);

-- 3. APPLICATIONS TABLE
CREATE TYPE triage_decision AS ENUM ('GREEN', 'YELLOW', 'RED');
CREATE TYPE application_status AS ENUM ('DRAFT', 'SUBMITTED', 'AUTO_APPROVED', 'UNDER_DWO_REVIEW', 'APPROVED', 'REJECTED', 'DISBURSED');

CREATE TABLE applications (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    application_number VARCHAR(50) UNIQUE NOT NULL, -- 'APP-2026-XXXXX'
    student_id UUID REFERENCES users(id) ON DELETE CASCADE,
    scheme_id UUID REFERENCES schemes(id),
    institute_name VARCHAR(255) NOT NULL,
    course_name VARCHAR(255) NOT NULL,
    annual_income NUMERIC(12, 2) NOT NULL,
    claimed_caste VARCHAR(100) NOT NULL,
    state VARCHAR(100) NOT NULL,
    district VARCHAR(100) NOT NULL,
    
    -- AI Forensic Metrics
    trust_score NUMERIC(5, 2) NOT NULL, -- 0.00 to 100.00
    triage_band triage_decision NOT NULL,
    status application_status DEFAULT 'SUBMITTED',
    
    -- Sub-Scores
    qr_integrity_score NUMERIC(5, 2),
    ela_tamper_score NUMERIC(5, 2),
    identity_match_score NUMERIC(5, 2),
    gazette_compliance_score NUMERIC(5, 2),
    dbt_readiness_score NUMERIC(5, 2),
    
    -- Verification Artifacts
    audit_trail JSONB NOT NULL DEFAULT '[]'::jsonb,
    is_dbt_ready BOOLEAN DEFAULT FALSE,
    submitted_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 4. VERIFIED DOCUMENTS TABLE
CREATE TYPE doc_type AS ENUM ('AADHAAR', 'CASTE_CERTIFICATE', 'INCOME_CERTIFICATE', 'DOMICILE', 'MARKSHEET');

CREATE TABLE documents (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    application_id UUID REFERENCES applications(id) ON DELETE CASCADE,
    document_type doc_type NOT NULL,
    s3_storage_uri VARCHAR(512) NOT NULL,
    s3_heatmap_uri VARCHAR(512),
    is_qr_present BOOLEAN DEFAULT FALSE,
    qr_payload TEXT,
    ocr_extracted_fields JSONB DEFAULT '{}'::jsonb,
    is_tampered BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 5. AUDIT & DISBURSEMENT LEDGER (Tamper-Proof)
CREATE TABLE disbursement_ledger (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    application_id UUID REFERENCES applications(id),
    sanctioned_amount NUMERIC(12, 2) NOT NULL,
    pfms_transaction_id VARCHAR(100) UNIQUE,
    dbt_account_last4 CHAR(4) NOT NULL,
    officer_id UUID REFERENCES users(id),
    disbursement_status VARCHAR(50) DEFAULT 'PROCESSING',
    previous_block_hash CHAR(64) NOT NULL,
    current_block_hash CHAR(64) NOT NULL,
    timestamp TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_apps_status_triage ON applications(status, triage_band);
CREATE INDEX idx_apps_student ON applications(student_id);
CREATE INDEX idx_users_aadhaar ON users(aadhaar_hash);
```

| # | Jury Trap Question | Strategic Engineering Response |

| **1** | *"If an applicant creates a completely fake certificate from scratch with matching name and caste, how will your ELA catch it?"* | *"ELA detects digital Photoshop splicing on existing documents. However, our system does not rely on a single signal. If a certificate is forged from scratch, it will fail **Stage 3 (QR Cryptography)** because state government certificates contain an asymmetric digital signature from the revenue authority. An attacker cannot forge the government's private key. If they omit the QR, our composite scorer penalizes the document by 35 points, pushing it directly into the Yellow/Red triage queue."* |
| **2** | *"How does this comply with the DPDP Act 2023 regarding Aadhaar storage?"* | *"We implement a Zero-Knowledge architectural model. The raw 12-digit Aadhaar number is never written to persistent disk storage or application databases. In-memory workers immediately redact the first 8 digits, storing only the compliant format `XXXX-XXXX-1234`. For cross-application deduplication, we compute an irreversible salted SHA-256 hash using a secret ministry master key."* |
| **3** | *"What happens when 20 Lakh students apply on the last day? Your server will crash."* | *"Traditional synchronous portals crash because file uploads block server worker threads. TribalSetu implements an asynchronous decoupled architecture using FastAPI, NGINX, and Redis/RabbitMQ buffers. Ingestion takes only 80ms to store the file and return a tracking token. Background verification is handled by Celery workers horizontally autoscaled via Kubernetes HPA. 46 worker pods of 16 cores each digest 20 Lakh applications in under 5 hours without server degradation."* |
| **4** | *"Rural tribal students often possess handwritten, stamp-based certificates from the 1990s without QR codes. Will your system reject them?"* | *"No. TribalSetu is designed for tribal inclusivity. When Stage 3 detects no digital QR, it does not mark the document as fraud; instead, it assigns the designated non-digital fallback score (70/100) and routes the document to the **YELLOW Queue**. The District Welfare Officer is presented with an optimized 10-second inspection interface with the stamp and signature pre-zoomed, cutting review time by 90% without rejecting genuine tribal beneficiaries."* |
| **5** | *"Why not use large multimodal LLMs (like GPT-4 Vision) for everything?"* | *"Large multimodal LLMs introduce three fatal architectural flaws for sovereign governance: First, cost—processing 90 Lakh documents via commercial LLM APIs would cost crores in recurring API billing. Second, data sovereignty—sending citizen identity documents to third-party cloud servers violates DPDP Act mandates. Third, hallucination—LLMs cannot provide court-admissible pixel-level mathematical variance proofs. TribalSetu uses sovereign, explainable algorithms (OpenCV, ELA, zxing-cpp) running locally at zero cost per scan."* |
